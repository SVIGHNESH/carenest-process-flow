Phone sign-up: app implementation guide

Written 2026-10-09 for the developer of the CareNest customer app (care_nest/, Flutter).

The backend side lives in DRAPP-BACKEND/ and is described in section 7 of its README.md.

1Summary

Customers now sign up and log in with a phone number and a 6-digit SMS code. There is no password and no email step. The backend for this is finished. This guide covers what the app must change to use it.

What the app has to do:

  1. Replace the login and register screens with one "Enter your phone number" screen.
  2. Make the code screen work for a phone number (it is email-only today).
  3. Add a "What is your name?" screen, shown only for a new number.
  4. Keep a small "Log in with email" link for existing customers, followed by a one-time "confirm your phone" step.
  5. Stop assuming every account has an email. User.fromJson crashes today on a phone-only account.

Nothing changes for the nurse app (cn_nurse/) or the admin dashboard. State management stays on Provider. The BLoC migration in flow.md is a separate piece of work.

3API reference: phone sign-up and login

Three public endpoints cover both sign-up and login. All take and return JSON. None needs an Authorization header. The base URL comes from API_BASE_URL in the app's .env, as today.

MethodPathPurpose
POST/auth/phone/send-otpText a 6-digit code to the number
POST/auth/phone/verify-otpCheck the code; log in a known number or return a signup token for a new one
POST/auth/phone/complete-signupCreate the account for a new number and log in

3.1 Send the code

POST /auth/phone/send-otp
{ "phone": "9876543210" }

200
{ "message": "OTP sent successfully", "expires_in_seconds": 600, "resend_in_seconds": 60 }

The server accepts 9876543210, +919876543210, 919876543210, 09876543210, and the same with spaces or dashes. It stores and returns every number as +91XXXXXXXXXX. Only Indian mobile numbers are accepted: 10 digits starting with 6, 7, 8 or 9. The response is the same whether or not the number has an account.

3.2 Verify the code

POST /auth/phone/verify-otp
{ "phone": "9876543210", "otp_code": "123456" }

Known number, the customer is logged in:

200
{ "is_new_user": false, "access_token": "<jwt>", "signup_token": null, "token_type": "bearer" }

New number, ask for a name next:

200
{ "is_new_user": true, "access_token": null, "signup_token": "<ticket>", "token_type": "bearer" }

Branch on is_new_user. Save access_token with ApiService.saveToken, exactly as the email login does today. Keep signup_token in memory only and pass it to the name screen. It is valid for 15 minutes. The server rejects it as an access token, so never save it as one. A code works once.

3.3 Complete sign-up (new numbers only)

POST /auth/phone/complete-signup
{ "signup_token": "<ticket>", "name": "Asha Verma" }

201
{ "access_token": "<jwt>", "token_type": "bearer" }

name is trimmed, must not be empty, and is at most 255 characters. Calling this twice with the same ticket is safe: the second call returns a token for the same account. After the token is saved, the session behaves exactly like today's. It is a 24-hour JWT, and the existing Dio interceptor adds the Bearer header.

4Errors and limits

Every error below except 422 returns { "detail": "<text>" }. The text is written to be shown to the customer as it is. Branch on the status code, not on the text.

WhenStatusdetailWhat the app should do
Number is not an Indian mobile number422a list, not a stringValidate on the device first; show "Enter a valid 10-digit mobile number"
Second code requested within 60 seconds429Please wait a minute before requesting another code.Keep Resend disabled; read Retry-After for the seconds left
More than 5 codes to one number in 10 minutes429Too many codes requested. Try again in a few minutes.Show the text; read Retry-After
More than 20 codes from one network address in 10 minutes429Too many codes requested. Try again in a few minutes.Same as above
SMS provider refused the message502Could not send the code. Please try again.Show the text; the customer may retry at once
Wrong code400Incorrect code.Clear the boxes, keep the customer on the screen
Code older than 10 minutes400This code has expired. Request a new one.Enable Resend
5 wrong tries on one code429Too many wrong attempts. Request a new code.Disable Verify, enable Resend
No unused code for this number400No code was requested. Request a new one.Enable Resend
The account is an admin403This account signs in with email and password.Show the text
Signup token invalid or older than 15 minutes400Signup session expired. Verify your number again.Go back to the phone screen

Two things in the current app code will break on these responses.

  • 422 has a list in detail. AuthService passes e.response?.data?['detail'] straight into a String? in AuthProvider. That throws when the value is a list and leaves the spinner running. Check detail is String before using it, and fall back to a fixed message.
  • There are two different 429s. One means "wait before resending" and comes from send-otp. The other means "this code is locked" and comes from verify-otp. Tell them apart by which call failed.

Retry-After is a response header holding whole seconds. With Dio, read it as e.response?.headers.value('retry-after').

For the timers on the code screen, take expires_in_seconds and resend_in_seconds from the send-otp response instead of hardcoding them.

5Existing email accounts

Customers who registered with email and password keep logging in that way, then confirm their phone number once. POST /auth/login is unchanged: { "email", "password" } in, { "access_token", "token_type" } out.

A number typed at the old registration was never checked, so the server ignores it for phone login. If such a customer types their number on the phone screen, they are treated as a new number and would create a second, empty account. The "Log in with email" link on the phone screen is how they avoid that, so keep it visible.

After an email login, call GET /users/me. If phone_verified is false, show the confirm-phone screen, prefilled with phone when it is not null. Both calls below need the Authorization: Bearer header, which the Dio interceptor already adds.

POST /users/me/phone/send-otp
{ "phone": "9876543210" }

200
{ "message": "OTP sent successfully", "expires_in_seconds": 600, "resend_in_seconds": 60 }
POST /users/me/phone/verify
{ "phone": "9876543210", "otp_code": "123456" }

200
<the updated profile, same shape as GET /users/me, with phone_verified true>

The limits and error texts are the same as in section 4, plus one more:

WhenStatusdetail
Another account has already verified this number409This number is already used by another account.

From then on the customer can use the phone screen. The email login keeps working too. A code requested here cannot be used on /auth/phone/verify-otp, and the reverse, so do not mix the two screens' calls.

POST /auth/register still exists so the released app version keeps working. The new app should not call it.

6Profile changes

6.1 GET /users/me

{
  "user_id": 1,
  "name": "Asha Verma",
  "email": null,
  "phone": "+919876543210",
  "email_verified": false,
  "phone_verified": true,
  "role": "user",
  "created_at": "2026-10-09T16:43:10.399556"
}
  • email can now be null. It is null for every account created with a phone number until the customer adds one.
  • phone can still be null, for old email accounts that never gave one.
  • email_verified and phone_verified are new and always present.

6.2 PATCH /users/me

name works as before. phone can only be changed here while phone_verified is false. Once the number is verified, a different phone value is rejected:

WhenStatusdetail
Changing a verified number400Your number is verified. Change it by verifying the new number.
Number is not an Indian mobile number400Enter a valid 10-digit mobile number

To change a verified number, use the two /users/me/phone/* calls from section 5 with the new number. Sending the same number back unchanged is accepted.

6.3 Adding an email

A phone account can add an email, confirmed with a code sent to that address. Both calls need the Bearer header.

POST /users/me/email/send-otp
{ "email": "asha@example.com" }

200
{ "message": "OTP sent successfully", "expires_in_seconds": 600, "resend_in_seconds": 60 }
POST /users/me/email/verify
{ "email": "asha@example.com", "otp_code": "123456" }

200
<the updated profile, with email set and email_verified true>

The other limits and code errors match section 4.

6.4 Bookings

Every booking response gains booked_by_phone next to booked_by_email. booked_by_email is null for phone-only customers.

8Testing against a local backend

The backend changes are not committed or deployed yet. The app's default API_BASE_URL (https://dr-backend-evhe.onrender.com) does not have the new endpoints until they are. Until then, run the backend locally.

  1. In DRAPP-BACKEND/, leave MSG91_AUTH_KEY empty in .env. With no key, no SMS is sent and the code is written to the server log instead.
  2. Start it with .venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000. Migrations run on startup.
  3. Point the app's .env at it. From the Android emulator the host machine is http://10.0.2.2:8000.
  4. Request a code in the app, then read it from the server log. The line looks like MSG91_AUTH_KEY unset; OTP for +919876543210 is 265152 (not sent).

Cases to walk through on a device:

  • New number: phone, code, name, Home.
  • Same number again: phone, code, straight to Home, same account.
  • Wrong code, then the right one.
  • Five wrong codes: Verify is refused until a new code is requested.
  • Resend inside 60 seconds is refused; after 60 seconds it works.
  • A code left for more than 10 minutes is refused as expired.
  • A number such as 12345 never reaches the server.
  • Closing the app on the name screen, reopening, and starting again from the phone screen.
  • Old account: email login, confirm phone, then log out and log in by phone into the same account.
  • Old account confirming a number that a phone account already owns: the 409 text is shown.
  • Phone-only account: Home, profile, a full booking and the Razorpay sheet all work with no email.
  • Airplane mode on each screen: an error is shown and the button comes back.

9Open points

  • Is the confirm-phone step mandatory? The server does not force it. An email account with phone_verified false can use every other endpoint. The plan says the app asks once after login; whether "Skip" is offered is a product decision.
  • Real SMS is untested. No MSG91 credentials exist yet, so delivery to a real phone has not been tried. SMS autofill on Android depends on the final approved template text.
  • Forgot password. Phone accounts have no password. For email accounts the server's POST /auth/forgot-password emails a reset link, which the current app does not use.
  • Lost number. A phone-only customer who loses their number cannot log in unless an admin helps. Encouraging customers to add an email (section 6.3) reduces this.
  • Google sign-in. POST /auth/google exists on the server and the app does not use it. This update leaves it alone.
